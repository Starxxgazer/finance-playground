# 三人协作指南

## 职责和目录边界

开发负责人定义内容格式、编写游戏程序、维护金融数值模型，并审查合并。
A、B 一起讨论故事；A 用 Codex 整理到内容文件，两人共同试玩，B 重点记录不吸引人、难理解或逻辑不通的位置。

当前内容入口是 `prototype/story.js`，素材放在 `prototype/assets/`。`app.js`、`model.js`、页面结构和测试由开发负责人维护。内容格式仍待双方讨论，不把当前结构视为最终标准。

涉及金额、期限或新玩法的改动，先在 PR 或任务中说明需要怎样的程序配合；不得仅改故事文字，留下不匹配的计算或结局。

## 第一次加入（A）

1. 登录自己的 GitHub 账号（当前邀请对象：`372785716aa-star`），接受 [仓库协作邀请](https://github.com/Starxxgazer/finance-playground/invitations)。无需把 GitHub 密码或 Token 发给任何人。
2. 在自己的电脑安装 Git、Node.js 22、Python 3。可以让 Codex 检查这些工具。
3. 运行 `git clone https://github.com/Starxxgazer/finance-playground.git`，然后 `cd finance-playground`。
4. 配置该仓库的作者信息：`git config user.name "你的名称"`、`git config user.email "你的 GitHub 提交邮箱"`。可用 GitHub Settings → Emails 中显示的 noreply 邮箱。
5. 按根目录 README 启动试玩并打开网页，确认原版能运行。

GitHub CLI 用户可用 `gh auth login` 交互登录；不要把 Token 写进远程仓库地址、代码或文档。

## 每轮故事修改

先确认工作区干净；如有未提交工作，先妥善提交，不能用强制重置清理。然后从最新主分支建立本轮分支，例如：

```bash
git switch main
git pull --ff-only origin main
git switch -c story/bakery-01
```

每轮使用新名字，下一轮可以是 `story/bakery-02`。开发负责人采用 `dev/功能名`。不需要额外的长期 develop 分支。

给 A 的 Codex 的任务示例：

> 阅读 AGENTS.md 和协作指南，在当前 story 分支根据我们的故事设计编辑内容。优先只改 story.js 和已约定素材；需要程序或金额模型配合时列出具体需求。保留现有改动，完成后运行自动检查，告诉我们怎样本地试玩，并展示提交差异。未经本次明确授权，不推送或合并。

修改后：

1. 运行根目录 README 的自动检查；A、B 亲自玩一遍，检查选项跳转、证据获取、相关结局和重玩。
2. 执行 `git status --short` 和 `git diff`，确认没有密钥、私人文件或非本任务改动。
3. 只暂存本轮文件。例如：

```bash
git add prototype/story.js
git diff --cached
git commit -m "story: 调整面包店调查对话"
git push -u origin story/bakery-01
```

4. 打开 GitHub 的 Compare & pull request，目标选 `main`，按模板写清改了什么、试玩了什么，请求 `Starxxgazer` 审查。
5. 开发负责人看差异并运行试玩；检查通过后使用 Squash and merge。故事 PR 获得批准后若继续改动，需要重新审查。

若主分支在此期间更新，可在自己的工作分支运行：

```bash
git fetch origin
git merge origin/main
```

有冲突时先理解两边改动，不要一键覆盖。同步后重跑检查与试玩，再正常推送，不强制推送。

## 主分支保护的目标设置

- 合并前需要自动检查 `prototype-check` 通过，且分支与最新 `main` 同步。
- 需要至少一人批准，并由 CODEOWNERS 中的负责人 `Starxxgazer` 审查。
- 新提交使旧批准失效，未解决的审查讨论阻止合并。
- 禁止普通协作者强制推送或删除 `main`。
- 仓库管理员保留 GitHub 默认的管理例外，以免唯一开发负责人的 PR 因不能自审而完全卡住；日常仍使用 PR、检查与试玩，不把例外当作常规流程。

CODEOWNERS 和分支保护约束合并，不是逐文件写权限。A 可以在自己的分支提出改动，最终由负责人审查。B 若只讨论和试玩，可不授予写权限。

## 提交前共识

- 自动检查只验证部分逻辑，是否好玩必须人工判断。
- 不推送官方手册、问答附件、个人资料、密钥、依赖文件夹和测试截图产物。
- 图片和其他素材记录来源；AI 辅助制作记录工具、用途与团队实际贡献。
- 多人使用各自的克隆。多个 Codex 会话共用一个目录时，不切换彼此的分支；需要不同分支同时开发，使用单独工作目录。
