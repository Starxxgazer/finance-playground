## 第一次加入

两位队友已接受邀请，均拥有写入权限。各自在自己的电脑运行：

    git clone https://github.com/Starxxgazer/finance-playground.git
    cd finance-playground

配置本仓库的 Git 作者名称和邮箱；推荐自己 GitHub Settings → Emails 显示的 noreply 邮箱。准备 Git 和 Python 3；其他环境等技术方案确定后再安装。

GitHub CLI 用户可通过 gh auth login 登录；不要把密码或 Token 发给别人，或写入代码、文档和远程地址。

## 每轮修改

确认工作区干净；有未提交工作先妥善保存，不能用强制重置丢弃。然后从最新主分支建立工作分支：

    git switch main
    git pull --ff-only origin main
    git switch -c story/design-01

每轮用新名称，例如 story/design-02；程序开发使用 dev/功能名，仓库维护使用 chore/任务名。多个会话共用目录时，不擅自切换彼此的分支。

给队友 Codex 的任务示例：

> 阅读 AGENTS.md 和协作指南，在当前工作分支整理讨论结果。当前先修改约定的文档；后续故事格式由开发负责人确定。不要恢复已否决的旧原型。保留现有改动，检查后展示差异；需要程序配合时列出明确需求。

完成后：

1. 运行 python3 .github/scripts/check_repository.py；Windows 可用 py。游戏实现后还需相应测试和真人试玩。
2. 用 git status --short、git diff 检查改动，确认无凭证、个人资料和非本任务文件。
3. 用 git add 逐项暂存本轮文件，执行 git diff --cached 核对，再提交、推送当前工作分支。
4. 在 GitHub 发起目标为 main 的 PR，说明改动和验证，请求 Starxxgazer 审查，由开发负责人合并。

主分支更新后，在工作分支执行 git fetch origin 和 git merge origin/main；有冲突先理解双方改动，解决后重新检查，不强制推送。

## 主分支保护

- 自动检查 prototype-check 必须通过，分支需与最新 main 同步。名称沿用原有配置，当前检查仓库文件和文档。
- 至少一人批准，并由 CODEOWNERS 中的 Starxxgazer 审查；新提交使旧批准失效。
- 未解决的审查讨论阻止合并；普通协作者不能强制推送或删除 main。
- 管理员保留 GitHub 默认的管理例外，避免唯一开发负责人的 PR 因不能自审卡住；日常仍使用 PR 和检查。

CODEOWNERS 约束合并，不是逐文件写权限。队友可以在自己的分支提出修改，最终由负责人审查。
