## 依次完成

1. 检查当前操作系统和终端，以及 Git、GitHub CLI、Python 3 是否可用。先识别当前目录是否已经是这个项目。若不是，默认在当前用户选定的工作目录下创建 finance-playground；目标目录若已存在，先检查它的 remote、分支和工作区，不覆盖。不要照搬负责人电脑的 /home/stargazer 路径。

2. 使用已有工具。Git、gh 或 Python 缺失时，先说明缺少什么，采用该系统的官方安装方式；需要管理员授权或会改变系统环境时等我完成那一步。当前不用安装 Node、前端框架或游戏依赖，因为游戏尚未实现。

3. 用 gh auth status 核实登录状态，再用 gh api user 只读取 login 和 id。若未登录，引导我通过 gh auth login 的浏览器/设备流程登录 GitHub.com；不要打印 Token。若登录的是 Starxxgazer 或不确定的账号，先让我确认并切换为自己的账号，不能借用他人身份继续。

4. 确认目标仓库存在，检查我的仓库权限是否包含 push。公开仓库能被克隆不代表拥有写权限。没有权限时，提供 https://github.com/Starxxgazer/finance-playground/invitations ，让我用正确账号接受邀请后再检查。

5. 如果尚未克隆，执行 git clone https://github.com/Starxxgazer/finance-playground.git，并进入目录。如果已经克隆，核对 origin 确实指向此仓库；SSH 或 HTTPS 都可以，不擅自替换其他仓库的远程地址。工作区有改动时保留现场，告诉我具体文件，不自动 stash、reset 或切换分支。

6. 读取 AGENTS.md、README.md、docs/协作指南.md。检查远程最新 main 是否已经有本提示词文件、docs/design/ 和 docs/standards/，且 prototype/ 已删除。如果仍是旧版，停止依赖新版本的配置，明确告诉我让负责人先合并清理和协作规范 PR，不在旧原型基础上开工。

7. 使用我的已核实 GitHub login 配置本仓库的 user.name；默认邮箱采用 GitHub 返回的数字 id 加上 login，即“ID+LOGIN@users.noreply.github.com”，只设置 --local。已有明确正确的本地署名可保留。设置本地 pull.ff=only、fetch.prune=true。不要复制负责人的姓名和邮箱。

8. 不在已有非目标分支或未提交状态下强行切换。工作区干净时，git fetch origin，再切到 main，用 git pull --ff-only origin main 同步。若 main 分叉或本地有额外提交，保留现场并说明，不能用 reset 覆盖。

9. 首次故事任务分支为 story/design-01，从最新 main 创建。若本地或远程已有同名分支，先检查它是否属于我的当前任务：符合则复用/建立跟踪，不符合则选择未占用的 story/design-02 等名称，不覆盖或强制移动分支。新分支刚建立时可以与 main 指向同一提交，不需要制造内容改动或空提交。

10. 使用当前系统可用的 Python 3 运行 .github/scripts/check_repository.py。因为当前没有游戏，只报告仓库检查结果，不声称完成试玩，也不要运行旧 prototype 的 npm 命令。

11. 用 git push -u origin 当前分支名推送我的工作分支并设置上游，验证远程分支和本地提交一致。如果 HTTPS 缺少凭证，在我已通过 gh 正确登录的前提下，仅为当前仓库配置调用 gh auth git-credential 的凭证助手，不把 Token 写入 remote，不擅自改全局凭证配置。SSH 不可用时说明问题，再使用同一目标仓库的 HTTPS。

12. 验收：工作目录正确、身份是我、拥有 push 权限、origin 正确、当前是 story/ 分支且跟踪对应 origin 分支、工作区干净、仓库检查通过。尚无内容差异时不要创建空 PR。

最后只告诉我：本地路径、GitHub 身份、当前分支、检查结果，以及还需要我亲自完成的步骤（如有）。这些结论必须来自实际检查，不以预选项或假设代替。
