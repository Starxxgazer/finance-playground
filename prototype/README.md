# 《这笔钱借给谁》网页试玩原型

这是用于验证趣味性的 **3–5分钟候选故事**，不是定稿产品。面包店只是首轮验证材料；现有根目录策划案、产品说明均保留。

## 立即试玩

在项目根目录执行：

```bash
cd prototype
python3 -m http.server 4173 --bind 127.0.0.1
```

浏览器打开 **http://127.0.0.1:4173**。也可以 `npm start`，不需要安装依赖。关闭服务按 `Ctrl+C`。

还可以直接双击 `prototype/index.html` 离线打开。进度存在当前标签页的 `sessionStorage` 中，刷新可继续；关闭标签页后可能清除。若浏览器限制本地文件存储，游戏仍能继续，只是不保证刷新恢复。想同时试不同路线，可以分别开新的浏览器会话。

手机与电脑在同一个可信局域网时，可在 `prototype/` 执行：

```bash
python3 -m http.server 4173 --bind 0.0.0.0
```

手机访问 `http://电脑的局域网IP:4173`。只服务 `prototype/` 目录；试玩完关闭服务。WSL 是否能直接从手机访问取决于主机网络配置，不需要为本次试玩发布网站。

## 3–5分钟演示路线

| 时间参考 | 操作 | 观察重点 |
| --- | --- | --- |
| 0:00–0:30 | 阅读开场，接下调查 | “扩张还是救急”是否让人想继续 |
| 0:30–1:40 | 走访三人；深挖老板排期、供应商记录 | 人物各自掌握局部事实，2次深挖有取舍 |
| 1:40–2:40 | 把余额放现在、尾款放明天、收支放未来30天；切换两种方案 | 未来的钱不能提前用；新店改变现金余量 |
| 2:40–3:20 | 用合同、尾款或排期追问老板 | 玩家拿证据推动对话 |
| 3:20–4:20 | 选建议、至少2张证据和1项剩余风险；提交 | 建议与依据分开评价 |
| 4:20–5:00 | 阅读来信和公司透视图；回溯一次选择 | 相同条件下比较另一种后果 |

这只是节奏目标，没有强制计时；还需要真人试玩测量实际阅读时长。不要先告诉玩家“正确选项”。游戏不设置单一胜利评分。

建议首次选“10万暂缓”，引用“设备尾款通知＋老店收支摘要”，保留“用途是否执行”的风险；再回溯选“20万立即扩张”。补充资料和拒绝的故事不同，计入同一类“不放款”结局。三类结局都可通过回溯抵达。

## 已实现的玩法

- 悬念开场、3名人物走访、2次可选深挖、最多8张可回看的证据。
- 事实、人物说法、经营预测分别标明来源与时间；没有调查的排期会明确标为未核实。
- 资金时间线可点击或拖放，放错有提示；手机和键盘都可完成。
- 两种贷款方案、证据追问、4项建议、结构化依据与剩余风险。
- 3类结局、4种后续来信、公司透视图、结局回溯及完整重玩。
- 手机适配、跟随系统的亮暗主题、减少动态效果、刷新恢复和存储失败降级。
- 纯HTML/CSS/JavaScript，无构建步骤、运行时第三方库、账号、后端、实时AI、埋点或外部网络请求。

## 内容入口与程序边界

目前的文件结构是原型实现选择，**正式剧情格式、协作格式由用户与队友后续讨论确定**，不要据此锁死方案。

最新分工：用户主开发；A、B共同设计故事；A用Codex本地试玩后提交到 `story` 分支，由用户检查合并。仓库与分支操作遵循根目录文档；本轮原型实现没有提交、切换分支或推送。

| 文件 | 作用与建议负责人 |
| --- | --- |
| `story.js` | A、B优先讨论的内容入口：人物、问题、回答、证据、建议标签、风险、结局来信。A修改后本地试玩。 |
| `assets/bakery.webp` | 本地开场插画；如换故事，应同步更换素材与替代文本。 |
| `app.js` | 用户负责：流程、调查次数、证据解锁、状态保存、UI渲染。开场、追问回应、公司透视图等仍有展示文案在这里；队友提出文案建议，由主开发整合。 |
| `model.js` | 用户负责：唯一资金计算与判断反馈规则，金额以千元整数存储。更改需同步测试、故事与文档。 |
| `styles.css` / `index.html` | 用户负责：布局、无障碍、主题、入口和弹窗。 |
| `tests/` | 数值与真实浏览器流程验收；不会修改剧情数据。 |
| `test-results/` | 本地验收报告和截图，供核查，不代表真人兴趣验证。 |

内容字段说明：`evidence` 的键、`people` 的键、`grants/deepGrants`、`choices` 的键、`category`、`risks` 的键都是程序引用的固定ID；不要仅为润色改名。可以先改 `title/text/source/question/answer/deep/deepAnswer/letter` 等文字。增加人物、证据、调查动作、结局类型或新金额属于程序变更，需要主开发同步调整。结局展示数字由 `model.js` 算出，不能用文案自行覆盖。

## 资金口径与关键规则

单位均为万元，沿用策划案。老店未来30天净流入：18 − 16 = 2。它不是当前余额，也不能解决明天付款。

| 方案 | 付完初始款项 | 未来30天末 |
| --- | --- | --- |
| 借20万并扩张 | 2 + 20 − 10 − 12 = 0 | 0 + 18 − 16 + 0 − 6 − 1.8 = **−5.8** |
| 借10万并暂缓 | 2 + 10 − 10 = 2 | 2 + 18 − 16 − 0.9 = **3.1** |
| 暂缓或拒绝，不放款 | 2 − 10 = **−8**，这是明天的付款缺口 | **未知**，没有假设展期或其他融资成功 |

- 设备尾款10万、新店首期12万、首月额外6万均单独计数，不包含在老店16万日常支出里。
- 18万收款、16万支出、开业排期都是预测。没有取得排期时，对比中的“新店首月0收款”明确标为保守情景，不冒充调查事实。
- 0.9万、1.8万是给定还款额，不推算利率；暂缓扩张方案需要专款支付和真实执行。
- 结局只说明给定约30天窗口，不保证全年安全。不放款不能自动推断倒闭。
- 全部公司、人物、合同、金额均虚构；不收集账户、资产或身份信息，不触及真实资金，不生成真实授信评级。
- 仅保存游戏状态，无用户输入HTML；恢复进度时验证ID、阶段及必要前提，损坏进度回到开场。
- 本地测试生成的浏览器profile含数据库，不属于交付，禁止提交；`.gitignore` 已排除依赖与相关临时目录。

## 测试与验收

数值单测仅需Node，无需安装依赖：

```bash
npm test
```

真实浏览器测试需要安装开发依赖及Chromium，并先启动上述HTTP服务：

```bash
npm ci
npx playwright install chromium
npm run test:e2e
```

也可以使用现有Chrome，例如Linux：

```bash
CHROME_PATH=/usr/bin/google-chrome npm run test:e2e
```

`TEST_URL` 可覆盖默认的 `http://127.0.0.1:4173`。浏览器测试会写入 `test-results/`。默认截图涵盖桌面、390px暗色手机、320px窄屏和四种后续来信。

Lighthouse只审计开场；游戏各阶段另用axe做无障碍检查：

```bash
TMPDIR=/tmp TEMP=/tmp TMP=/tmp CHROME_PATH=/usr/bin/google-chrome npx lighthouse http://127.0.0.1:4173 --quiet --chrome-flags="--headless --no-sandbox" --output=json --output-path=test-results/lighthouse.json --only-categories=performance,accessibility,best-practices
```

实际验收结果见 [TESTING.md](TESTING.md)。测试证明流程可达和计算一致；是否好玩、能否在3–5分钟理解，需要目标玩家继续验证。

## 真人试玩记录建议

不要求玩家提供姓名、账号或资产信息。A、B可用以下问题观察并记在本地，记录格式待团队讨论：

1. 开场30秒，玩家想查清什么？是否愿意继续？
2. 玩家先找了谁，为什么？有没有主动深挖、比较、回看证据？
3. 哪一步需要解释？手机按钮是否找得到？
4. 结尾请玩家复述：老店为什么缺钱，扩张为什么更危险？
5. 玩家是否主动想换选择？最想改的是故事、节奏还是操作？

当前没有自动收集或上传这些反馈。
